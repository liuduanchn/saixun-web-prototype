### 0.1 一审方案的事实性错误（已在本版修正）

| # | 原表述 | 实际情况 | 处置 |
|---|---|---|---|
| 1 | 「`AiModule` 需 `imports: [PrismaModule]`」 | `PrismaModule` 是 `@Global()`，`PrismaService` 全局可注入，**无需 import**（`RuntimeConfigModule` 同理） | 已删 |
| 2 | 「三个调用点传 `user.tenantId`」 | 4 处 AI 调用都在**私有方法**内，签名里没有 `user`，须先扩签名 | 已改，见第四节第 4 步 |
| 3 | 「加 `@Roles('OWNER','TEACHER')`」 | **该装饰器与 RolesGuard 都不存在**（`auth/decorators` 仅 `current-user`、`public`） | 已改为服务内校验，见第四节第 5 步 |

### 0.2 一审遗漏项（本版已补）

| # | 遗漏 | 严重度 |
|---|---|---|
| 1 | **LLM 调用无超时、无重试**：`openai-compat.service.ts` 用裸 `fetch`，无 `AbortController`；而 `speech.service.ts` 已有 60s 超时 + 503/504 退避 + 备用模型降级 | P1 |
| 2 | **验证命令用错请求头**：平台网关会给每个请求注入它自己的 `Authorization: Bearer …`，标准 Bearer **必然 401**，必须用 `x-saixun-auth` | P1（会误判实施失败） |
| 3 | **`/api/config/status` 是 `@Public`**：加租户级字段后会把租户模型/域名泄露给未登录者 | P1 |
| 4 | 前端 `DEMO_MODE` 分支未处理（`saveAsr` 开头有 `if (DEMO_MODE) return`） | P2 |
| 5 | `llmModelDiagnosis` 等分功能字段**没有定义解析规则**（谁读、怎么查表） | P2 |

### 0.3 实测发现的实施前置阻塞项

线上实测（教师与学生两个账号，均 HTTP 200 读到同一租户 `settings`）：

```
GET /api/tenants/me  →  {"id":"demo-tenant",...,"settings":{"asrApiKey":"","asrApiKeySet":false}}
```

`PATCH /tenants/me/settings` 的控制器只有 `@UseGuards(JwtAuthGuard)`，服务层无任何角色判断，
全仓库不存在 RolesGuard —— **学生账号具备写该接口的能力**。Key 一旦落进 `Tenant.settings`，
学生虽看不到明文（脱敏），却能清空/覆盖教师的 Key。**必须先补鉴权，再放 Key。**

## 二、方案选型

| 方案 | 做法 | 优点 | 缺点 | 适用性 |
|---|---|---|---|---|
| **A 租户级配置（推荐）** | 复用 `Tenant.settings`，新增 `llm*` 键，按活跃租户解析 | 与 ASR 完全同构、零新表、多租户天然隔离、学生不可见 | 每个租户各配一份 Key | 演示与多团队场景 |
| B 平台级单例 | 新建 `SystemConfig` 表或钉死一个平台租户 | 全站配一次 | 需新表 + 新接口；密钥集中，越权面大 | 单团队私有部署 |
| C 随包 `runtime.json` | 密钥随发布包携带 | 零改动 | 密钥落在平台与仓库，额度被盗风险高 | 不推荐 |

**推荐 A**：成本最低、复用已验证的安全逻辑、演示现场只需一次填写。

## 三、配置分层与字段定义

解析顺序（租户优先，因为线上唯一可用来源是 DB）：

## 四、后端改动（5 步）

**第 1 步｜新增 `server/src/config/llm-config.ts`**
导出 `resolveLlmConfig(tenantId)` 与 `llmStatus()`，复用 `runtime-config.ts` 的 `maskSecret()`，不新增脱敏实现。

```ts
export async function resolveLlmConfig(prisma: PrismaService, tenantId?: string) {
  const t = tenantId ? await prisma.tenant.findUnique({ where: { id: tenantId } }) : null;
  const s = parseJson<Record<string, string>>(t?.settings, {});
  const env = aiConfig();                        // 复用现有三级优先级
  return {
    baseUrl: (s.llmBaseUrl || env.baseUrl).replace(/\/$/, ''),
    apiKey:  s.llmApiKey || env.apiKey,
    model:   s.llmModel  || env.model,
    source:  s.llmApiKey ? 'tenant' : (env.apiKey ? 'env' : 'none'),
  };
}
```

**第 2 步｜`ai.interface.ts`** 给 `ChatOptions` 增 `tenantId?: string`，保持接口向后兼容（其余调用点无需改动）。

**第 3 步｜`openai-compat.service.ts`** 构造注入 `PrismaService`，把三个私有 `baseUrl()/apiKey()/model()` 换成 `await resolveLlmConfig(this.prisma, opts?.tenantId)`。
**`AiModule` 无需改**（`PrismaModule` 已是 `@Global()`）。无 Key 仍抛原异常，调用方 fallback 逻辑不变。

**第 3.5 步｜补超时与重试（一审遗漏，P1）** 照抄 `speech.service.ts` 的成熟做法：

```ts
const controller = new AbortController();
const timer = setTimeout(() => controller.abort(), 45_000);   // LLM 比 ASR 快，45s 够用
try {
  resp = await fetch(url, { method: 'POST', headers, body, signal: controller.signal });
} finally { clearTimeout(timer); }
// 429/503 退避重试 1 次（硅基流动高峰期常见），其余状态直接抛
```

**第 4 步｜4 个私有方法扩签名（不是「3 个调用点」）**

| 文件 | 现状 | 改法 |
|---|---|---|
| `criteria.service.ts:112` | `private callAi(text)` | → `callAi(text, tenantId)`；调用处 `:80` 传 `user.tenantId` |
| `diagnosis.service.ts:120` | `private callAi(points, content, cases = [])` | 追加第 4 参 `tenantId`；调用处传 `user.tenantId` |
| `defense.service.ts:129` | `private callAiFirstQuestion(pointList, workText)` | 追加 `tenantId` 参数 |
| `defense.service.ts:265` 附近 | 评分/总评那个私有方法 | 追加 `tenantId` 参数 |

四处内部均为 `this.ai.chat(messages, { temperature, maxTokens, tenantId })`。Controller 层不动。

**第 5 步｜状态接口与权限**
- `config.controller.ts` 的 `@Public` `status()` **只保留 env 层的非敏感信息**；租户级信息（`llmBaseHost / llmModel / llmApiKeySet`）另开一个**受 JWT 保护**的 `GET /api/config/llm`，避免把租户配置暴露给未登录者。
- `config.controller.ts` 新增 `POST /api/config/llm-test`（受保护 + `@Throttle` 限流）：用当前租户配置发一次 `max_tokens: 8` 的最小请求，返回 `{ ok, latencyMs, message }`。
- `tenants.service.ts`：`presentSettings()` 扩展 `llmApiKey → maskSecretValue()` + `llmApiKeySet`（**P0，漏了就是明文下发前端**）；`updateSettings()` 的「`****` 结尾 → 保留原值」分支扩展到 `llmApiKey`。
- **权限收紧（前置阻塞项）**：`auth/decorators` 下**没有** `@Roles`，不建议为此新建装饰器 + 守卫。直接在 `TenantsService.updateSettings` 顶部用**已存在**的能力判断：

```ts
const m = await this.users.getMembership(user.tenantId, user.sub);   // 已存在的方法
if (!m || !['OWNER', 'TEACHER'].includes(m.role)) {
  throw new ForbiddenException('仅团队负责人或指导教师可修改集成配置');
}
```

> 注意用 `membership.role`（成员在本租户内的角色），不要用 `user.role`（JWT 里的账号级角色，两者在多租户下会不一致）。

## 六、安全与权限

密钥只进后端 DB，前端只拿脱敏值与布尔标记；「`****` 结尾视为未修改」避免打开设置页直接保存把真 Key 覆盖成 `sk-****`；写入限 OWNER/TEACHER；`llm-test` 接口限已登录用户且做频次上限（防把 Key 当免费代理刷）。剩余风险：链接公开，Key 存在被他人写入滥用的可能，建议填**低额度**专用 Key 并在演示后轮换。

## 七、验证方法（实施后逐条实测）

**⚠️ 请求头必须用 `x-saixun-auth`，不能用标准 `Authorization: Bearer`。**
平台网关会给每个请求注入它自己的 `Authorization: Bearer eyJ…`，passport 取到的是网关令牌，
验签必然 `invalid signature`，表现为「登录成功但所有带 token 的请求 401」。
这条已写死在 `jwt.strategy.ts` 的 `AUTH_HEADER` 注释里，一套命令写错会误判成实施失败。

```bash
BASE=https://saixun-cabin.app.workbuddy.host
T=$(curl -s --noproxy '*' -X POST $BASE/api/auth/login -H 'Content-Type: application/json' \
     -d '{"username":"teacher","password":"123456"}' \
   | python -c "import sys,json;sys.stdout.write(json.load(sys.stdin)['access_token'])" | tr -d '\r\n')
# 注意：登录接口有加严限流，连续探测会被 429，需间隔
curl -s --noproxy '*' $BASE/api/tenants/me -H "x-saixun-auth: $T"
```

| 步骤 | 命令／操作 | 通过标准 |
|---|---|---|
| 1 | 设置中心填硅基流动 Key → 保存 | 刷新后 Key 显示为 `sk-****`，且 `llmApiKeySet:true` |
| 2 | `GET /api/config/llm`（带 `x-saixun-auth`） | `llmBaseHost:api.siliconflow.cn, source:tenant` |
| 3 | 点「测试连接」调 `POST /api/config/llm-test` | `{ok:true, latencyMs:…}` |
| 4 | 赛项解析页点「AI 解析评分要素」 | 返回要素名不再是固定 5 要素模板 |
| 5 | 学生账号 `student1` 调 `PATCH /tenants/me/settings` | 403 拒绝（当前实测为可读 200，属待修） |
| 6 | **重新发布一次线上实例**，重读第 2 步 | 配置仍在 → 确认 SQLite 跨「重新发布」持久 |

**已完成的实测基线（2026-10-04）**：`/api/config/status` → `aiConfigured:false, source:none`；
`/api/health` → `db:up`；教师与学生两个账号 `GET /api/tenants/me` 均 200，`settings` 为 `{asrApiKey:"", asrApiKeySet:false}`。

## 七之二、两个待定项的解析规则（一审未定义）

**分功能模型**：`ChatOptions` 增可选 `feature?: 'criteria' | 'diagnosis' | 'defense'`，
由 `resolveLlmConfig` 按 `llmModel + '_' + feature` 查表，命中则覆盖 `model`，未命中回落 `llmModel`。
这样调用点只需多传一个枚举，规则集中在配置层。

**前端 `DEMO_MODE`**：`saveAsr` 开头是 `if (DEMO_MODE) { onToast(...); return; }`，新的 `saveLlm` 必须同样处理，
否则未连后端时点保存会静默无反馈。

## 八、实施顺序、风险与待确认问题

**建议实施顺序（顺序本身是安全要求，不可颠倒）**

| 序 | 内容 | 理由 |
|---|---|---|
| 1 | 设置写接口补角色校验 + `presentSettings` 加 `llmApiKey` 脱敏 | 阻塞项，先堵权限口子再放 Key |
| 2 | `llm-config.ts` + `chat()` 支持租户配置（含超时） | 后端能力，可独立验证 |
| 3 | 4 处私有方法扩签名传 `tenantId` | 打通链路 |
| 4 | 设置中心面板 + `/api/config/llm` + `llm-test` | 前端可见 |
| 5 | 重新发布一次，验证第 6 步持久性 | 确认运维含义 |

**风险**：① 线上 SQLite 是否跨「重新发布」持久**尚未自证**（我无法在不写入线上库的前提下验证），若不持久，运维含义是「每次重发布后需重填一次 Key」，需你接受；② 密钥存平台 DB，链接公开，务必用**低额度专用 Key**，演示后轮换；③ 降级启发式的输出是确定性的，接真模型后每次结果会变，可能影响答辩截图的可复现性。
